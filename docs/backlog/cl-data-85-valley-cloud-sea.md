# CL-DATA-85 — 山頂＋谷地雙格點雲海模型

**狀態**：backlog（owner 2026-11-27 裁示：列後續規格，不阻塞主站）
**來源**：物理稽核官 2026-11-26 體檢；CL-PHYS-02/03 施工期間的殘留風險

## 問題

單一 Open-Meteo 格點只描述「視點所在那一格」的大氣。雲海的本體是**谷地**的雲層，
它不在那一格裡。因此在峰頂格點上：

- `base_asl = grid_elevation + LCL` 永遠 ≥ 格點地面，數學上不可能低於山頂。
  以 2,160 個取樣格點計算，雲海判據的「雲頂低於視點」條件只剩 12 格成立。
- CL-PHYS-02 因此讓雲頂高於視點時**誠實回 UNKNOWN（資料不足）**，這是 owner 選定的
  方案 A。結果是 17 個雲海題材在整份 bundle 出現 **168/168 小時 UNKNOWN**，
  全 bundle 只有 1 個雲海推薦小時，而那小時本身低雲 79%、雲頂低於視點 18 m
  —— 等於站在雲裡被推薦看雲海。
- CL-PHYS-03 接手後，雲海改以 RH850/RH925 ≥ 90% ＋ 低雲 ≥ 60% 為主判據，
  但「觀測點在雲內」的硬否決會先一步把低雲 ≥ 80% 或 RH850 ≥ 95% 的日子判為
  ✕ 雲霧籠罩，於是雲海實際可 PASS 的區間窄到 RH 90–94% ∧ 低雲 60–79%。

## 提議做法

1. 每個雲海景點增加**谷地代表點**（與視點同一個 forecast 請求的第二組座標，
   取視線方向 or 已知谷地位置；存進 `data/v2/policy/valley_points.json`，
   不可改 pinned canonical record）。
2. 谷地格點取 LCL + 低雲量 → 得到真正的 `valley_deck_asl`；
   `summit_elevation > valley_deck_asl + margin` 才是雲海的正條件。
3. 觀測點是否在雲內仍由山頂格點決定（CL-PHYS-02 的既有 gate 不動）——
   兩者分開判定：**山頂乾、谷地有雲 = 雲海；山頂濕 = 不宜**。
4. 過渡期：谷地點缺失時回 UNKNOWN，不可回 PASS，也不可回 FAIL。

## 驗收標準

- 合歡山／阿里山／大屯山三個示範景點，在「谷地有雲、山頂乾」的真實歷史日中
  必須給出 ✓ 推薦，且推薦時段與實際雲海出現時段重疊（以實拍時間比對）。
- 白牆日（山頂在雲內）仍必須是 ✕ 不宜 · 雲霧籠罩，回歸測試沿用
  `test_cl_phys_02_datum_in_cloud.py` 的大屯山 fixture。
- 雲海題材的 168 小時 UNKNOWN 比例從 ~100% 降到 < 60%（谷地點缺失時仍可 abstain）。
- 不得新增 pin 漂移：新資料只進 `data/v2/policy/**`。

## 風險

- 谷地座標選錯（例如選到另一個山頭）會製造比現在更糟的誤報，必須有可視化驗證。
- 每個景點多一次 provider 呼叫 → 459 景點的成本上升；可只對 `genre_template=cloud_sea`
  的 17 個題材做。
